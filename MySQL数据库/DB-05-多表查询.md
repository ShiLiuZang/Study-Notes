# DB-05：多表查询

> 本节目标：根据主外键关系连接业务表，正确选择 `INNER JOIN`、`LEFT JOIN`、子查询、`EXISTS` 和 `UNION ALL`，并避免错误连接与一对多计数问题。

## 1. 连接关系

当前三张表的连接路径：

```text
users.id
    ↑
knowledge_bases.user_id

knowledge_bases.id
    ↑
documents.knowledge_base_id
```

连接时必须让外键与它引用的主键比较，不能因为两列都叫 `id` 就随意连接。

## 2. INNER JOIN

查询未删除文档及其知识库名称：

```sql
SELECT
    d.id,
    d.title,
    kb.name AS knowledge_base_name
FROM documents AS d
INNER JOIN knowledge_bases AS kb
    ON d.knowledge_base_id = kb.id
WHERE d.deleted_at IS NULL;
```

`INNER JOIN` 只返回两边成功匹配的记录。

- `d`、`kb` 是表别名。
- `knowledge_base_name` 是结果列别名。
- 多表查询应使用 `d.id`、`kb.id` 等限定列名，避免歧义。

## 3. LEFT JOIN

查询所有用户及其知识库，即使用户还没有知识库：

```sql
SELECT
    u.id,
    u.email,
    kb.id AS knowledge_base_id,
    kb.name AS knowledge_base_name
FROM users AS u
LEFT JOIN knowledge_bases AS kb
    ON kb.user_id = u.id;
```

`LEFT JOIN` 保留左表的所有记录；右表没有匹配时，右表字段显示为 `NULL`。

查找没有知识库的用户：

```sql
SELECT
    u.id,
    u.email
FROM users AS u
LEFT JOIN knowledge_bases AS kb
    ON kb.user_id = u.id
WHERE kb.id IS NULL;
```

## 4. ON 与 WHERE

- `ON`：决定右表哪些记录参与连接。
- `WHERE`：连接完成后过滤最终结果。

显示所有知识库，但只连接未删除的 `processing` 文档：

```sql
SELECT
    kb.id,
    kb.name,
    d.id AS document_id,
    d.title AS document_title
FROM knowledge_bases AS kb
LEFT JOIN documents AS d
    ON d.knowledge_base_id = kb.id
   AND d.deleted_at IS NULL
   AND d.status = 'processing';
```

右表筛选条件放在 `ON` 中，没有符合条件文档的知识库仍会保留。若把 `d.status = 'processing'` 放入 `WHERE`，没有匹配文档的知识库会被过滤，左连接效果接近内连接。

## 5. 一对多展开与正确计数

一个知识库有三篇文档，连接结果就会出现三行知识库信息。这是一对多关系的正常展开，不是数据库产生了重复记录。

统计每个知识库的 `ready` 活动文档，包括数量为零的知识库：

```sql
SELECT
    kb.id,
    kb.name,
    COUNT(d.id) AS ready_document_count
FROM knowledge_bases AS kb
LEFT JOIN documents AS d
    ON d.knowledge_base_id = kb.id
   AND d.deleted_at IS NULL
   AND d.status = 'ready'
GROUP BY kb.id, kb.name
ORDER BY ready_document_count DESC, kb.id ASC;
```

这里使用 `COUNT(d.id)`，因为右表没有匹配时 `d.id` 为 `NULL`，计数正确得到 `0`。`COUNT(*)` 会把左连接保留的占位行计为 `1`。

分组后不能随意按未分组、未聚合的 `d.id` 排序。本题的稳定排序使用知识库主键 `kb.id`。

## 6. 三表连接与笛卡尔积

查询 `ready` 活动文档、所属知识库和用户邮箱：

```sql
SELECT
    u.email,
    kb.name AS knowledge_base_name,
    d.id AS document_id,
    d.title AS document_title
FROM users AS u
INNER JOIN knowledge_bases AS kb
    ON kb.user_id = u.id
INNER JOIN documents AS d
    ON d.knowledge_base_id = kb.id
WHERE d.status = 'ready'
  AND d.deleted_at IS NULL
ORDER BY d.id ASC;
```

每增加一张有关联的表，都要写出对应连接条件。结果数量异常大时，优先检查：

- 是否漏写连接条件。
- 是否连接了语义不同的字段。
- 是否只是正常的一对多展开。

若每一行左表记录都与每一行右表记录任意组合，就形成笛卡尔积；结果行数会按表的行数相乘。

## 7. 标量子查询

查询用户 `1` 的指定知识库中的活动文档：

```sql
SELECT id, title
FROM documents
WHERE deleted_at IS NULL
  AND knowledge_base_id = (
      SELECT id
      FROM knowledge_bases
      WHERE user_id = 1
        AND name = 'Python 后端资料'
  );
```

`=` 右侧的标量子查询必须最多返回一个值。`knowledge_bases` 的 `UNIQUE(user_id, name)` 保证内层条件最多找到一行。

若子查询返回多个 ID，不能写成 `column = (多行结果)`；可以根据语义改用 `IN` 或 `EXISTS`。

- 只用另一张表的结果过滤：可以使用子查询。
- 还需要显示另一张表的列：通常使用 `JOIN` 更直接。

## 8. EXISTS 与 NOT EXISTS

查询至少拥有一篇 `ready` 活动文档的知识库：

```sql
SELECT
    kb.id,
    kb.name
FROM knowledge_bases AS kb
WHERE EXISTS (
    SELECT 1
    FROM documents AS d
    WHERE d.knowledge_base_id = kb.id
      AND d.status = 'ready'
      AND d.deleted_at IS NULL
);
```

- `EXISTS`：至少存在一条符合条件的记录。
- `NOT EXISTS`：一条符合条件的记录都不存在。

`EXISTS` 只关心是否存在记录，因此内层通常写 `SELECT 1`。内层引用外层的 `kb.id`，这是相关子查询。

## 9. UNION 与 UNION ALL

合并 `ready` 和 `processing` 活动文档：

```sql
SELECT id, title, status
FROM documents
WHERE deleted_at IS NULL
  AND status = 'ready'

UNION ALL

SELECT id, title, status
FROM documents
WHERE deleted_at IS NULL
  AND status = 'processing'

ORDER BY id DESC;
```

- `UNION`：合并后删除完全重复的结果行。
- `UNION ALL`：保留全部结果，通常开销更小。

参与合并的查询必须返回相同数量的列，对应位置类型需要兼容。最终列名由第一个 `SELECT` 决定，整体排序写在最后。

当前例子直接使用 `status IN ('ready', 'processing')` 更简单；`UNION` 更适合合并不同查询或不同表中结构兼容的结果。

## 10. 本轮易错点

- 把表别名误当成结果列别名。
- 错写为 `knowledge_bases.user_id = documents.id`，混淆用户 ID 和文档 ID。
- `SELECT` 列之间漏写逗号。
- 多表查询未限定 `deleted_at` 属于哪张表。
- 为保留左表记录，却把右表筛选条件放进 `WHERE`。
- 左连接计数使用 `COUNT(*)`，使没有子记录的父记录得到 `1`。
- 排序时写成 `d.id`，而题目要求 `kb.id`，并把 `ASC` 拼成 `AESC`。
- 三表查询漏掉 `d.deleted_at IS NULL`。
- 标量子查询查询了错误的 `users` 表；知识库名称属于 `knowledge_bases`。
- 把“至少存在”写成 `NOT EXISTS`。
- 使用 `d.deleted_at = NULL`，而不是 `IS NULL`。

检查方法：先沿外键画出连接路径，再逐项检查“返回列、连接条件、业务过滤、分组计数、排序”。
