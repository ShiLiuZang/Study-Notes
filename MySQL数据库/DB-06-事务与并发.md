# DB-06：事务与并发

> 本节目标：理解 ACID、自动提交、隔离级别和常见并发现象；会使用原子更新与 `SELECT ... FOR UPDATE`；知道如何缩短事务并处理死锁。

## 1. ACID

- 原子性 Atomicity：事务中的操作要么全部提交，要么全部撤销。
- 一致性 Consistency：提交或回滚后，数据库仍满足外键、唯一、状态等规则。
- 隔离性 Isolation：并发事务之间的可见性和干扰受隔离级别与锁控制。
- 持久性 Durability：`COMMIT` 成功后，结果应持久保存。

创建知识库和第一篇文档如果属于同一业务动作，就应当同成同败。第二步失败并执行 `ROLLBACK` 后，第一步也不能留下记录。

## 2. COMMIT、ROLLBACK 与自动提交

```sql
SELECT @@autocommit;
```

默认结果通常为 `1`。在没有显式事务时，一条成功的 DML 通常会立即提交，之后执行 `ROLLBACK` 无法撤销：

```sql
UPDATE documents
SET status = 'processing'
WHERE id = 1;

ROLLBACK;
```

如果初始状态是 `pending`，最终仍是 `processing`。

显式事务：

```sql
START TRANSACTION;

UPDATE documents
SET status = 'processing'
WHERE id = 1;

ROLLBACK;
```

这里回滚后恢复为 `pending`。如果先执行 `COMMIT`，后续 `ROLLBACK` 不能撤销已经提交的数据。

事务属于数据库连接；连接 A 的事务不能由连接 B 回滚。以后使用 SQLAlchemy 时，一个事务内必须使用同一个 Session。

## 3. 并发读取现象

### 3.1 脏读

事务 B 读到了事务 A 尚未提交、随后被回滚的数据：

```text
脏读 = 读取其他事务尚未提交的数据
```

主要可能发生在 `READ UNCOMMITTED`。

### 3.2 不可重复读

事务 B 在同一事务中两次读取同一行；事务 A 在中间提交了修改，导致 B 两次读到不同内容：

```text
不可重复读 = 同一行前后值发生变化
```

它不是脏读，因为事务 A 的修改已经提交。

### 3.3 幻读

事务 B 两次执行相同范围查询；事务 A 在中间插入或删除并提交，导致第二次查询的行集合增加或减少：

```text
幻读 = 范围查询的结果集合发生变化
```

不可重复读关注同一行的值，幻读关注符合条件的行集合。

### 3.4 丢失更新

两个事务都基于同一份旧数据修改，后提交的结果覆盖先提交的结果：

```text
A 读取旧值 → B 读取旧值 → A 提交 → B 根据旧值提交并覆盖 A
```

解决方向包括条件原子更新、悲观锁和乐观锁。

## 4. 四种隔离级别

从弱到强：

```text
READ UNCOMMITTED  读未提交
READ COMMITTED    读已提交
REPEATABLE READ   可重复读
SERIALIZABLE      串行化
```

MySQL InnoDB 默认使用 `REPEATABLE READ`：

```sql
SELECT @@transaction_isolation;
```

为下一次事务设置隔离级别：

```sql
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
START TRANSACTION;
-- SQL
COMMIT;
```

- `READ UNCOMMITTED` 可能脏读。
- `READ COMMITTED` 的每次普通一致性读取建立新快照，可能出现不可重复读和幻读。
- `REPEATABLE READ` 的普通一致性读取在同一事务中通常使用第一次读取建立的快照。
- `SERIALIZABLE` 最严格，但可能带来更多等待和更低并发。

InnoDB 的普通快照读、加锁读和写操作并不完全采用相同视图。`REPEATABLE READ` 下的范围加锁操作还可能使用 gap lock 或 next-key lock；当前只掌握行为边界，不研究 MVCC 与锁算法源码。

## 5. 条件原子更新

简单状态迁移优先尝试单条条件更新：

```sql
UPDATE documents
SET status = 'processing'
WHERE id = 1
  AND status = 'pending'
  AND deleted_at IS NULL;
```

两个请求同时竞争时，通常只有一个能够匹配旧状态并成功修改。应用必须检查受影响行数：`1` 表示成功取得状态迁移，`0` 表示记录不存在、已删除或已被其他请求改变。

## 6. SELECT ... FOR UPDATE

需要“先读取、再根据读取结果执行多步写入”时，可以在显式事务中进行加锁读取：

```sql
START TRANSACTION;

SELECT id, status
FROM documents
WHERE id = 1
FOR UPDATE;

UPDATE documents
SET status = 'processing'
WHERE id = 1;

COMMIT;
```

匹配记录通常会保持锁定，直到事务提交或回滚；其他事务修改同一行时可能等待。

要求：

- 必须使用显式事务。
- 查询、修改和提交必须使用同一连接。
- 事务尽量短。
- 不持有数据库锁等待模型 API、PDF 解析或其他耗时外部 I/O。

## 7. 死锁

```text
事务 A：锁文档 1 → 等待文档 2
事务 B：锁文档 2 → 等待文档 1
```

双方循环等待就是死锁。InnoDB 通常自动检测死锁，并选择一个事务回滚以打破循环。

应用处理：

- 捕获死锁错误。
- 回滚失败事务。
- 对整个事务做有限次数重试，而不是只重试最后一条语句。
- 多行操作按照一致顺序加锁，例如始终按主键升序。
- 使用合适索引并缩短事务。

## 8. 完整事务边界

创建知识库和第一篇文档：

```sql
START TRANSACTION;

INSERT INTO knowledge_bases (
    user_id,
    name,
    description
)
VALUES (
    1,
    'MySQL 学习资料',
    '保存 MySQL 学习笔记'
);

SET @knowledge_base_id = LAST_INSERT_ID();

INSERT INTO documents (
    knowledge_base_id,
    title,
    raw_content,
    content_hash,
    status
)
VALUES (
    @knowledge_base_id,
    '事务笔记',
    '事务保证多步数据库操作同成同败',
    'hash_transaction_note',
    'pending'
);

COMMIT;
```

第二条插入失败时必须执行 `ROLLBACK`，知识库记录也会撤销。`LAST_INSERT_ID()` 获取当前连接刚产生的自增 ID。

事务边界建议：

```text
事务开始前：读取文件、解析 PDF、计算哈希
事务内部：执行必须同成同败的数据库检查和写入
事务提交后：调用 Embedding API、执行耗时后台任务
```

“插入文档并更新相关数据库状态”适合放进事务；“执行相关写入后立即提交”是短事务原则。模型调用和大型文件解析不应占用数据库事务。

## 9. 本轮易错点

- 认为 `autocommit = 1` 时，成功的单条更新仍能被后续 `ROLLBACK` 撤销。
- 把 InnoDB 默认隔离级别记成 `READ COMMITTED`；正确值是 `REPEATABLE READ`。
- 忽略事务属于单个连接或 Session。
- 只重试死锁事务的最后一条语句，而不是回滚并重试整个事务。
- 把长时间模型调用和 PDF 解析放进持锁事务。
- 只选择“立即提交”，遗漏了事务内部应该包含相关数据库写入。
